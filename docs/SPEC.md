# Technical spec

## Categories (fixed, exactly 10)

Chosen because they mirror freedesktop.org's Desktop Menu Specification "Main Categories" (the vocabulary KDE, GNOME, AppStream and Flatpak/Flathub already use), so classification isn't invented from scratch:

`Development`, `Education`, `Graphics`, `Internet`, `Games`, `Multimedia`, `Office`, `Science`, `System`, `Utilities`

Freedesktop → our label mapping used when assigning categories: `AudioVideo → Multimedia`, `Network → Internet`, `Game → Games`, `Utility → Utilities`; `Development`, `Education`, `Graphics`, `Office`, `Science`, `System` map by name directly.

Display order on screen is this fixed order; empty categories (no installed apps) are skipped, not shown empty.

## Catalog schema — `src/data/catalog.json`

Flat JSON array, one object per app. The file is **generated** by `tools/build_catalog.py` from `tools/sources/` (see "Data sources"), so it is not edited by hand: a hand edit is overwritten by the next build. Corrections go into the tables at the top of `build_catalog.py` instead — `NAME_OVERRIDES`, `CATEGORY_OVERRIDES`, `EXCLUDED_IDS`, `CLI_ID_OVERRIDES`, `EXISTS_ON_WINDOWS`, `WINDOWS_START_NAMES` and `RENAMED_FROM` — which are reviewable and tested.

```json
{
  "id": "firefox",
  "name": "Firefox",
  "vendor": "Mozilla",
  "category": "Internet",
  "bin": { "linux": "firefox", "windows": "firefox.exe", "macos": "Firefox" },
  "icon": "firefox.png",
  "hidden": false,
  "cli": false
}
```

| Field      | Meaning                                                                                                                                                                                                                                                                                                            |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id`       | Stable slug, also used as the icon-lookup key by convention (`icon` can override)                                                                                                                                                                                                                                  |
| `name`     | Display title on the tile                                                                                                                                                                                                                                                                                          |
| `vendor`   | Provenance only (Mozilla, KDE, GNOME, Microsoft, Apple, etc.) — not used for grouping in v1, kept for future "by company" view if ever wanted                                                                                                                                                                      |
| `category` | One of the 10 fixed categories above                                                                                                                                                                                                                                                                               |
| `bin`      | Per-OS launch identifier, keyed `linux`/`windows`/`macos` — **any key can be absent**, meaning the app doesn't exist on that OS. On Linux/Windows it's the executable name checked on `$PATH`; on macOS it's the `.app` bundle's display name (no `$PATH` for GUI apps there — see "Cross-platform support" below) |
| `icon`     | Filename under `src/assets/icons/` (always PNG, see "Icon format"); if missing at runtime, frontend falls back to `assets/icons/category/<category>.png`                                                                                                                                                                              |
| `aka`      | Optional. Ids this entry used to have (`RENAMED_FROM` in `build_catalog.py`). Scan-derived ids follow the cleaned display name, so a better name changes the id; on startup the frontend moves any rename/hide/recategorise the user saved under an old id to the new one, instead of silently orphaning it. Add a line there whenever an id changes.                                                                                                                                                                                                       |
| `hidden`   | Manual override to hide an entry without deleting it                                                                                                                                                                                                                                                               |
| `cli`      | Terminal-only tool (no real GUI icon will ever exist for it) — frontend shows the dedicated `assets/icons/category/cli-tool.png` glyph instead of trying `icon`/category fallback, so it reads as "no icon expected" rather than "icon missing by accident"                                                        |

## Data sources for seeding the catalog

- `tools/sources/desktop-pkgs.json` — vendored snapshot of the user-supplied dataset (originally `https://raw.githubusercontent.com/interneto/tui-toolbox-installer/refs/heads/main/interneto_install/data/desktop-pkgs.json`). ~250 apps, each with `name`, `category`, `subcategory`, and package identifiers across 11 package managers (apt, pacman, AUR, dnf, emerge, flatpak, snap, brew, winget, nix, freebsd pkg). For Linux `bin` values, prefer the apt/pacman/flatpak id (usually equals the package name; a handful will need manual correction where the binary name differs from the package name).
- `tools/sources/vendor_apps.json` — hand-written entries not covered by the dataset above: KDE apps (Dolphin, Konsole, Kate, Okular, Spectacle, KCalc), GNOME apps (Files/Nautilus, Console, Text Editor, Calculator, Loupe), and ~65 Microsoft/Apple entries (`win-*`/`mac-*` ids, most single-platform placeholders; Edge/PowerShell/OneDrive have a real, hand-verified triple across all three OSes). Each entry's `bin` is already the per-OS object described above. An entry can set an explicit `"icon"` (e.g. `"konsole.svg"`) to override the default `<id>.png` guess — used for the KDE apps, see the icon pipeline note below. This file (and its breeze-icons downloads) is now mostly a **portability fallback**: it's what a fresh clone has before anyone runs the system scan below on their own machine.
- `tools/sources/category_map.json` — one-time mapping table from the dataset's own `category`/`subcategory` strings to our 10 labels. Built by dumping the dataset's unique category values once and assigning each by hand.
- `tools/sources/system_apps.json` — **generated**, not hand-written: the output of `tools/scan_system_apps.py` scanning this machine's actual installed `.desktop` files (see "System app scan" below). Machine-specific, regenerate after installing new software.

`tools/build_catalog.py` merges all of these into `src/data/catalog.json`, with `system_apps.json` entries winning any bin collision (they're ground truth for this machine — see the merge-priority note below). It is run manually/occasionally — not part of the running app, and re-running it should not silently blow away hand-edits the user has made directly to `catalog.json` (diff before overwriting, or merge by `id`).

A final pass drops anything in `EXCLUDED_IDS` (in `build_catalog.py`), applied after all sources are merged so it catches an unwanted id regardless of where it came from. This is for curation, not correctness: near-duplicates of something already covered by a better entry (extra KDE Connect variants, KWrite when Kate exists), obscure single-purpose sub-editors bundled with a bigger suite (Kontact/KMail's Contact Print/Theme Editor, Header Theme Editor, Sieve Editor, Import Wizard), crash-reporter applets (GNOME's and KDE's), and onboarding/meta-config tools that aren't really "apps" a user would deliberately launch (Welcome Center, KDebugSettings, Journald Browser, Menu Editor, Input Method Selector, SELinux Troubleshooter). Extend this set by hand as more low-value clutter turns up in a system scan — it's a judgment call, not a rule, so don't try to generalize it into a heuristic.

### Apple/Microsoft placeholder entries

`vendor_apps.json` also carries `mac-*` and `win-*` ids for common Apple and Microsoft apps that don't exist on every OS (Safari, Finder, Pages... / Notepad, Paint, Microsoft Word...). Most only have one key in their `bin` object (`{"macos": "Safari"}` or `{"windows": "notepad.exe"}`) — genuinely single-platform apps, not a gap. On Linux, `is_installed` returns `false` for these immediately since there's no `linux` key at all, so they stay correctly hidden there with zero cost. See "Cross-platform support" below for the Windows/macOS implementation itself — Windows is now verified on real hardware, macOS is not.

## System app scan — `tools/scan_system_apps.py`

The curated dataset only knows ~250 well-known apps, which undercounts what's actually installed on a real desktop. Every Linux desktop already has a complete, authoritative list of that: the XDG `.desktop` files each installed package drops into `/usr/share/applications` (plus `/usr/local/share/applications`, `~/.local/share/applications`, and the flatpak/snap equivalents). Each one already carries a `Name=`, a `Categories=` (the same freedesktop vocabulary our 10 categories map from — see `FREEDESKTOP_CATEGORY_MAP`), an `Exec=` (first token, with field codes like `%f`/`%U` stripped, becomes `bin`), and an `Icon=` that the *active icon theme* resolves to a real file already on disk. Reading this is strictly better than guessing: no classification heuristics needed, no network calls, and it's exactly what KDE/GNOME's own app menu shows.

- Icon resolution: an absolute `Icon=` path is used directly; a theme icon name is searched across `~/.local/share/icons`, `~/.icons`, `/usr/share/icons`, `/usr/local/share/icons` — trying the machine's actual active theme first (KDE via `kreadconfig6`/`kreadconfig5 --file kdeglobals --group Icons --key Theme`, e.g. `breeze-dark`; GNOME via `gsettings get org.gnome.desktop.interface icon-theme`, each skipped safely if its tool isn't installed), then `breeze`, `Adwaita`, `hicolor` — checking both real-world directory layouts seen in practice (hicolor-style `<size>/apps/<name>.<ext>` and breeze-style `apps/<size>/<name>.<ext>`), then `/usr/share/pixmaps/<name>.<ext>` as a last resort. Only the KDE path has actually been exercised (this machine); the GNOME check is written to degrade safely but is otherwise unverified.
- Every resolved icon is copied into `src/assets/icons/` — the **one shared icon folder**, same as every other source — named `<desktop-file-id><ext>`, so the lookup happens once per install and the running app just reads a local file like any other entry; re-running the scan skips files already copied.
- Merge priority in `build_catalog.py`: dataset → vendor_apps.json → **the matching system scan wins last**, keyed by `bin[os_key]` via a shared `merge_system_scan(by_bin, entries, os_key)` helper (see "Windows/macOS system scans" below — same function handles all three OS scans, not just Linux's). A system-scanned Dolphin/Konsole/Kate/etc. replaces the dataset/vendor guess's Linux name+icon+category; anything with no prior entry for that bin is added as new. Critically, this is a **merge into the existing `bin` object, not a wholesale replacement** — a dataset entry's `windows`/`macos` guess is preserved and only the matching OS's key gets overwritten with the system-scanned value (this was a real bug initially: Firefox and VS Code's Windows/macOS bins were getting silently dropped because the system-scanned Linux entry was replacing the whole object). On this development machine this took the catalog from 268 to 322 entries (54 new, ~18 upgraded with a real icon), then to 352 after Phase 1.3 curation.
- This machine's own `app-launcher.desktop` shortcut also shows up in the scan (self-referential) and is explicitly excluded (`EXCLUDED_IDS`, shared with the general curation list — see "Data sources" above).
- Known limitation, not yet handled: a `.desktop` file with `Terminal=true` (mostly TUI tools that still ship a menu entry, e.g. `btop`) gets scanned and given a real icon, but `launch_app` spawns the bin directly with no terminal attached — clicking it won't show anything useful. Not fixed yet since it wasn't the ask that prompted this scan; flagged in `ROADMAP.md`.

## Windows/macOS system scans — Windows verified, macOS not

Analogous to `scan_system_apps.py` above, but for the other two OSes. The
Windows one has now been run against a real machine; the macOS one has not, so
it stays reviewed-code rather than confirmed-working.

- **`tools/scan_system_apps_macos.py`** — reads each `/Applications`/`/System/Applications`/`~/Applications` bundle's `Contents/Info.plist` via `plistlib` (pure Python stdlib, no macOS-specific module needed) for `CFBundleName`/`CFBundleDisplayName` (name), the bundle's own filename stem (bin, what `open -a "<name>"` expects), and `LSApplicationCategoryType` (an App Store category UTI like `public.app-category.developer-tools`, mapped to our 10 categories the same way freedesktop's `Categories=` is on Linux — `APP_CATEGORY_MAP`, defaulting unmapped ones to Utilities). Because `plistlib` is pure Python, the *parsing logic* — not the real-world result — is actually testable here: `python3 scan_system_apps_macos.py --self-test` builds a synthetic `.app` bundle with a hand-written `Info.plist` in a temp dir and asserts the name/bin/category/icon-path all come out right. That passing is real evidence the plist-reading logic is correct; it is not evidence that every real Info.plist in the wild matches this shape. Icon extraction is not implemented — a bundle's `.icns` would need conversion to something a browser `<img>` can render (`sips`/`iconutil`, both macOS-only tools this machine doesn't have either), so every entry currently falls back to the category glyph.
- **`tools/scan_system_apps_windows.py`** — enumerates the registry's `Uninstall` keys (`HKLM\...\Uninstall`, `HKLM\...\WOW6432Node\...\Uninstall` for 32-bit apps, `HKCU\...\Uninstall` for per-user installs) via `winreg`. **Now verified on real Windows** (Phase 3): 68 installed programs found. Registry `Uninstall` entries are meant for uninstalling, not launching, so `bin` is a best-effort extraction from `DisplayIcon` (usually `"C:\path\app.exe,0"` — the `,N` resource-index suffix is stripped); entries with no plausible `.exe` path are skipped rather than guessed at.
  - **Icon extraction**: the app's own icon is pulled from the `.exe`'s embedded resources via `PrivateExtractIcons` at 256×256, shelled out to PowerShell (pure Python can't read a PE resource section, and this avoids a pywin32/Pillow dependency). Deliberately *not* `ExtractAssociatedIcon`, which always returns a blurry 32×32 regardless of what the exe embeds. Verified: 65 of 68 apps produced a clean 256×256 PNG.
  - **Noise filtering**: the registry registers runtimes, redistributables, drivers and update packages exactly like real apps. `SystemComponent=1` catches some, but `.NET Runtime`/`ASP.NET Core`/VC++ redistributables don't set it, so `NON_APP_NAME_PATTERNS` filters them by name.
  - **Display-name cleaning**: the registry appends version/arch/locale noise. `clean_name()` strips it, with **order mattering** — the `(x64)`/`(64bit)` suffix must go *before* the `$`-anchored version patterns, or `"Golden Cheetah v3.8 (64bit)"` keeps its version. A bare year is preserved (`"Microsoft Office Home 2024"`) since it's part of the product name.
  - **Category inference**: there is no registry equivalent of a category, so `guess_category()` applies ordered keyword rules (specific before general). Without it every added app landed in Utilities.
  - **Ids** are readable slugs derived from the cleaned name, not the registry key — which is frequently a GUID (`win-{c7054d61-...}`) or an Inno Setup `..._is1` suffix.
- **`build_catalog.py` integration**: `main()` loads `system_apps_windows.json`/`system_apps_macos.json` the same optional way as `system_apps.json` (empty list if the file doesn't exist — which it won't unless someone actually runs these scans on a matching machine) and merges each through the same `merge_system_scan()` helper with `os_key="windows"`/`"macos"` respectively.
- **`tools/backfill_icons.py`** — a scan only sees apps the registry lists under its Uninstall keys. Plenty of launchable apps never appear there: Office's Word/Excel/PowerPoint/OneNote install as one suite and register only in the `App Paths` key, so they had a working launch target but no icon and rendered as a placeholder. This walks the catalog, resolves each Windows entry the same way the app does (`$PATH`, then `App Paths`), and extracts the icon from the executable's own resources for anything still missing one — 12 icons on this machine. It stages into `tools/icon_cache/`; `place_scan_icons()` adopts a cache entry keyed by the catalog id too, so these are placed and pruned by the same pass as scan icons.
- **Matching a scanned app to a curated entry**: for Windows the merge tries the executable basename first, then the **normalized display name** — and the name is what actually works. Curated entries rarely carry a `bin.windows` (the dataset only supplies one when it happened to list a winget id *and* the name looked like a bare executable), so a basename-only match found **0** of 68 scanned apps, while the name join found 63. Everything unmatched became a brand-new entry carrying the scan's inferred category, which is why GIMP, Steam, Spotify, OBS and Android Studio all landed in "Utilities" before this was fixed. `normalize_name()` lowercases, drops alphanumerics-only noise (`microsoft`, `mozilla`, `user`, `community`, `desktop`, `x64`...), locale tags (`en-US`) and a trailing year, so `"Microsoft Visual Studio Code (User)"` meets `"Visual Studio Code"`.
- **On a match, only the launch path and icon are taken** — the curated name and category win, since the registry supplies neither well (`"7-Zip 26.03 (x64)"`, always "Utilities").

## Icon pipeline

Priority order, each tried in sequence per catalog entry, all resolved **once at authoring time** — the running app never touches the network:

1. **dashboard-icons** (`homarr-labs/dashboard-icons`, Apache-2.0 — checked against the repository, an earlier version of this document wrongly said CC0 — git-clonable): `https://cdn.jsdelivr.net/gh/homarr-labs/dashboard-icons/png/<slug>.png`. Primary source, ~1800 apps covered, purpose-built for exactly this (app-dashboard tiles).
2. **Iconify's `simple-icons` set** (CC0-1.0 for the collection; the brand marks themselves remain their owners' trademarks), via the public render endpoint `https://api.iconify.design/simple-icons/<slug>.svg` — tried under a couple of slug variants (hyphens/underscores stripped, since simple-icons names rarely match our ids verbatim, e.g. `intellij-idea` → `intellijidea`). These are monochrome brand glyphs; loaded via `<img>`, their `fill="currentColor"` does **not** inherit the page's CSS color (an external image document is style-isolated), so they render as a flat black shape — still a real, recognizable logo rather than a generic category glyph.
3. **UXWing** (free for commercial use, no attribution required, but no bulk API — hand-pick one icon at a time): available for one-off per-app icons if you want to improve on a specific miss, but not used for bulk fetching.
4. **Magnific AI** (user's existing subscription): manual last resort to generate/upscale a one-off icon for anything still missing after 1–3. Dropped into `src/assets/icons/` by hand.

**Actual priority in practice is now**: local system icon theme (via `scan_system_apps.py`, see below — exact match, zero network, wins on this machine for anything with a `.desktop` file) → dashboard-icons → Iconify simple-icons → hand-picked UXWing/Magnific AI → generated fallback glyph. Steps 1–2 are fully automated in `tools/sync_icons.py`; the list above is what a *fresh clone on a different machine* falls back through before anyone runs the system scan there.

**`sync_icons.py` skips entries that can never display an icon anyway**: `cli: true` entries (they always show the dedicated CLI glyph, never a fetched one) and any entry with no `linux` key in `bin` (Apple/Microsoft placeholders — no point spending a network lookup on something that can't show up on this OS).

**Real bug hit while broadening coverage**: jsDelivr rate-limits bursts of concurrent requests with a `403` that's indistinguishable from a genuine miss unless you check the status code — an early pass mis-marked several very common apps (`vlc`, `obs-studio`, `wine`, `teamviewer`, `kdenlive`, ...) as absent from dashboard-icons purely because of rate-limiting, not because they were actually missing. Fixed by retrying non-404 failures a couple of times with backoff before accepting them as a real miss, and dropping concurrency from 16 to 6 workers. A few of those (`vlc`, `obs-studio`'s dashboard-icons entry specifically, `mpv`, `nmap`, `meld`, `timeshift`) turned out to be genuine misses even after retrying — dashboard-icons' focus is more on self-hosted *services* than general desktop GUI apps, which is a real, not rate-limit-related, gap.

**Another bug from the same pass**: `build_catalog.py`'s icon-field assignment defaulted every entry to `<id>.png` regardless of what `sync_icons.py` actually vendored — so an entry that got an Iconify `.svg` (like `gnome-terminal`) kept pointing at a nonexistent `.png` in `catalog.json`, silently falling through to the category glyph instead of showing the real icon that was sitting right there on disk. Fixed with a `default_icon()` helper that checks which extension actually exists on disk before writing the `icon` field, applied to both dataset- and vendor-derived entries (`ICON_OVERRIDES`/an entry's own explicit `"icon"` still take priority over this). Worth checking after any icon-pipeline change: does `catalog.json`'s `icon` field extension actually match the file `sync_icons.py` produced?

**Implementation note:** the 10 generic per-category fallback glyphs actually shipped as hand-authored SVGs, rasterized to PNG (`tools/gen_category_glyphs.py` → `src/assets/icons/category/<Category>.png`, source archived to `tools/icon_sources/category/<Category>.svg` — see "Icon format" below), plus an 11th dedicated `cli-tool.png` glyph for entries flagged `"cli": true` — zero licensing questions, zero network dependency, trivially regenerable. Current `sync_icons.py` coverage: 176/291 Linux-relevant non-CLI catalog entries have a real vendored icon (up from the original 108/270 dashboard-icons-only pass); most of the remaining misses are less-common apps neither source covers, plus CLI tools which now get the dedicated CLI glyph instead of a generic category fallback (see `is_cli()` in `build_catalog.py`: dataset subcategories `"CLI Utility"` and `"Compiler"` (e.g. `gcc` — no meaningful icon exists for a compiler), plus a small manual `CLI_ID_OVERRIDES` list for tools tagged otherwise, e.g. `btop`/`htop`/`fastfetch`/`neofetch`/`rsync`/`tmux`/`tree`/`curl` — these last four have no GUI and will never have a branded icon, so they get the base CLI glyph rather than a generic category one).

**Bug already hit once, worth remembering:** SVG text content is XML — a raw `<` or `>` in a label (the Development glyph's `</>` originally) makes the file invalid XML that silently fails to parse. The failure is easy to miss because it looks like a *missing* icon, not a *broken* one: the primary icon 404s (expected), `onerror` fires and points at the category glyph, that also fails to render, but the handler already cleared itself after the first failure — so instead of a second fallback you get the browser's raw "broken image" placeholder. Fixed by running every label through `xml.sax.saxutils.escape()` in `gen_category_glyphs.py`. If a fallback icon ever looks broken instead of just generic, check whether the SVG itself is valid XML before assuming it's a missing-file problem.

**KDE app icons**: dashboard-icons and Iconify have no coverage for KDE's own desktop apps (Konsole, Kate, Okular, Spectacle, KCalc, Gwenview, Elisa) — confirmed by direct lookup. `vendor_apps.json` sources these straight from KDE's own **breeze-icons** repo (`github.com/KDE/breeze-icons`, LGPL, `icons/apps/48/*.svg`, converted to `.png` by hand at the time — this predates the automated archive-and-convert pipeline, so there's no `tools/icon_sources/` entry for these specifically) via a per-entry `icon` override, and `ICON_OVERRIDES` in `build_catalog.py` does the same for dataset-derived entries (Gwenview, Elisa) — the portability fallback for a machine where the system scan hasn't run yet. Note some breeze-icons paths are themselves symlink aliases (e.g. `kcalc.svg` → `accessories-calculator.svg`, `spectacle.svg` → `ksnapshot.svg`); `raw.githubusercontent.com` serves a symlink's *target path as plain text*, not the real file, so always check the fetched content actually starts with `<svg`/`<?xml` before trusting it. On this machine the system scan now supersedes all of these with the real local theme icon anyway.

Explicitly **not used for bulk/automated fetching**: SVGRepo — its icons are aggregated from many sources with mixed, icon-by-icon licensing and no site-wide grant, which is incompatible with an unattended sync script. Fine to use manually if a specific icon's license is checked first, but `sync_icons.py` should not scrape it.

### Which entries are CLI tools

`cli: true` decides whether a tile lives under CLI Tools and opens in a terminal. The rule is *does clicking it show anything*: a program that prints usage and exits (`git`, `bun`, `pandoc`, `nmap`, `starship`) or has no window needs the terminal wrapper. It is a hand-kept list (`CLI_ID_OVERRIDES` in `build_catalog.py`, applied to every entry including scan-created ones), not a PE-header check: darktable, scrcpy and UltraStar are *console-subsystem exes that are really GUI apps*, and would be misfiled. Interactive shells are included too: launched without a console of their own they read EOF and exit at once (PowerShell "did not open"). `windows_cli_spawn` gives a shell (`pwsh`, `powershell`, `cmd`, `wsl`, `bash`) its own window with `start "" <exe>`, and wraps every other tool in `cmd /k` so its output stays readable.

### Shipped vs. generated on the machine

Icons are **shipped, not generated per machine**: everything in
`src/assets/icons/` is produced at authoring time (the scans and `sync_icons.py`
run on the maintainer's machine) and committed, so the app is deterministic,
works offline, and looks the same everywhere. Two consequences worth knowing:

- An icon extracted by the Windows scan is only useful if the same app exists
  on the user's machine; the launch target it came from is what decides that.
- A tile that resolves locally but has **no shipped icon** used to show the
  category glyph. On Windows the running app now closes that gap itself:
  when an `<img>` fails, `main.js` calls the `get_icon` command, which resolves
  the exe and runs `src-tauri/src/extract_icon.ps1` (the same script the scan
  uses) with `CREATE_NO_WINDOW`, caches the PNG under `app_cache_dir()/icons/`,
  and returns a `data:` URL (already allowed by the CSP). Packaged (MSIX/UWP/Store) apps such as MusicBee and Microsoft Store have no exe: their AppID is `<family>!<app>`, and `extract_appx_icon.ps1` reads the package manifest's `Square44x44Logo` and picks the largest plain variant (`targetsize-256`, unplated preferred). An exe under `WindowsApps` is an app-execution alias (a 0-byte reparse point with no icon), so it takes that route too. A failed extraction
  leaves a `<id>.none` marker so it isn't retried every launch — for a week, then it is retried. Linux and macOS
  return nothing and keep the category glyph — see `ROADMAP.md`.

### Icon format: PNG only, vector sources archived

Every icon the app actually ships — dashboard-icons, Iconify, the system-theme scan, the 10 generated category glyphs, the CLI-tool glyph — is normalized to **PNG** at vendoring time (via `magick`/ImageMagick), so `src/assets/icons/` is uniform: no per-icon "is this svg or png" branching anywhere in `main.js` or `build_catalog.py`. This wasn't the original design (earlier phases mixed PNG and SVG, whichever the source happened to provide) — unified after the fact once the mix started causing real bugs (see the two above: the XML-escaping bug and the icon-extension mismatch bug, both a direct consequence of two formats needing separate handling).

Any icon whose original source was a **vector** (Iconify SVGs, the hand-authored category/CLI glyphs, and system-theme icons that happened to be SVG) has its source archived to `tools/icon_sources/` (mirroring the same flat `<id>.svg` / `category/<Category>.svg` layout) before being rasterized — not shipped with the app, not read by anything at runtime, kept only because a vector is losslessly re-editable/re-scalable and a rasterized PNG isn't. Concretely:

- `tools/gen_category_glyphs.py` writes the SVG to the archive, then calls `magick <svg> -background none -resize 128x128 <png>` for the shipped copy.
- `tools/sync_icons.py`'s Iconify tier does the same: archive the fetched SVG bytes, rasterize to the PNG that actually goes in `src/assets/icons/`.
- `tools/scan_system_apps.py` archives+rasterizes only when the resolved theme icon is itself an SVG (common for breeze); already-raster theme icons (some hicolor ones are PNG) are just copied straight across, nothing to archive. The system theme itself is the permanent, always-re-derivable source for these either way — the archive here is a completeness nicety, not a backstop against data loss the way it is for network-fetched SVGs.
- `dashboard-icons` never enters the SVG path at all — only its `png/` variant is ever fetched.

`ImageMagick` (`magick`) is a hard dependency of these three maintenance scripts (not of the running app). All 128×128, `-background none` to preserve transparency where the source has any (the hand-authored glyphs are opaque anyway; Iconify brand marks are typically transparent outside the glyph strokes).

### Icon naming: one invariant, enforced by `build_catalog.py`

**Every file directly inside `src/assets/icons/` is named `<catalog-id>.png`, and every one is referenced by a catalog entry.** `category/` is the exception — it holds the 11 fallback glyphs (10 categories + `cli-tool`), which are referenced by convention rather than from any entry's `icon` field.

This is enforced, not just documented. `place_scan_icons()` in `build_catalog.py` runs at the end of every build and:

1. Copies any icon a system scan staged into `tools/icon_cache/` out to `ICONS_DIR/<id>.png`, using the id that *actually references* it.
2. Deletes every top-level file not in the referenced set.

The reason this exists: the Windows scan originally named shipped files after the *registry display name*, so `win-microsoft-visual-studio-code-user.png` was referenced by the entry `visual-studio-code` — nothing linked the two but the JSON — and every app the catalog later dropped or excluded left its icon behind. That had accumulated **62 orphan files (1.4 MB)**, plus `win-*` names that didn't correspond to any id. The scan no longer writes into `src/assets/icons/` at all: it stages into `tools/icon_cache/` (gitignored, rebuildable), because it doesn't know an app's final catalog id — only the merge does.

Content-hash auditing also surfaced 9 groups of byte-identical icons, which turned out to be real duplicate *apps* (the Kontact/KMail suite sharing one icon across several sub-tools) rather than naming accidents; those ids were added to `EXCLUDED_IDS` instead. After the fix: **0 orphans, 0 name/id mismatches, 0 duplicate content.**


## Rust backend — `src-tauri/src/lib.rs`

Two Tauri commands, intentionally minimal, both taking a `PlatformBin { linux: Option<String>, windows: Option<String>, macos: Option<String> }` (deserialized straight from the catalog entry's `bin` object — the frontend never needs to know which OS it's running on, it just forwards `entry.bin` as-is):

- `is_installed(bin: PlatformBin, name: Option<String>) -> bool` — `name` is the catalog display name, used only on Windows (see the Start Menu bullet). `bin.for_current_os()` (matches on `std::env::consts::OS`) returns `None` → `false` immediately with no further check. Otherwise:
  - **Linux**: `which::which(name)` — `$PATH` only, which is how desktop apps are launched there.
  - **macOS**: checks for a `<name>.app` bundle under `/Applications`, `/System/Applications`, `$HOME/Applications` via plain `Path::exists()` (no `$PATH` for GUI apps there).
  - **Windows**: `%VAR%` references are expanded first (`expand_env`), because the scan writes per-user launch paths as `%LOCALAPPDATA%\...`/`%APPDATA%\...`/`%USERPROFILE%\...` rather than one machine's `C:\Users\<name>\...`. An absolute path (what the system scan produces) just has to exist. A bare name is searched on `$PATH` via `which::which` (Windows-aware — checks `PATHEXT`, so a bare `git` resolves `git.exe`), then in the registry's **`App Paths` key** (`HKCU` + `HKLM`, 64-bit and `WOW6432Node` views). That key is how most GUI installers — Office, VLC, Inkscape — register themselves for the `Run` dialog, and they are *not* on `$PATH`; a PATH-only search reported them as not installed, so they never appeared (86 → 92 of 210 entries after adding it). Note the value is usually an **unquoted path containing spaces**, so the full string is tried before its first whitespace-delimited token — splitting up front truncates `C:\Program Files\VideoLAN\VLC\vlc.exe` to `C:\Program` and silently reports the app as missing.
- Called once per catalog entry from the frontend at startup (not a system scan — a targeted lookup against a known, finite list of ids from `catalog.json`).
- `launch_app(bin: PlatformBin, cli: bool) -> Result<(), String>` — macOS: `Command::new("open").args(["-a", name]).spawn()`. Linux **when `cli` is false**: `Command::new(name).spawn()`, same as before. When `cli` is true, see "CLI tools open in a terminal" below — a bare CLI tool spawned with no terminal attached is why "clicking `tree` does nothing" was a real complaint (see `RELEASES.md`). **Windows** resolves through the same registry lookup first, because spawning a bare `vlc.exe` fails even when `is_installed` just reported it as present. Any error is returned as a string for the frontend to display, never a panic/crash.

### CLI tools open in a terminal, not bare

A `cli: true` entry has no window of its own — spawned directly, its output goes nowhere anyone can see and the process exits (or hangs) invisibly. `linux_terminal_spawn(bin)` instead tries a fixed list of terminal emulators in order (`konsole`, `gnome-terminal`, `xfce4-terminal`, `alacritty`, `kitty`, checked via `which::which`; `xterm` last since it's least likely to already be installed on a modern desktop) and runs the tool inside whichever is found first, wrapped as `bash -c "<bin>; echo; read -n1 -s -r -p 'Press any key to close...'"` so the window doesn't vanish the instant a quick command like `tree` finishes (xterm gets `-hold` instead, which does the same job natively). If no terminal is found at all, returns an error rather than silently failing. **Verified working**: manually confirmed via `konsole -e bash -c "tree /tmp; ..."` — real output, window stayed open with the close prompt, screenshotted.

Windows gets the analogous `cmd /k <exe>` (stays open at a prompt afterwards), launched through `cmd /c start "" cmd /k <exe>` (`windows_cli_spawn`). **Verified on real hardware** by clicking the tiles in the running app (`tools/drive_app.js`). The `start` indirection matters: a direct `cmd /k` child inherits the app's null standard handles, reads EOF and closes the instant the program exits, so `pandoc`/`git` would flash and vanish. The exe is resolved to a full path first (`cmd` ignores App Paths, and Node.js is only reachable through the Start Menu). macOS is left as a bare `open -a` — `is_installed`'s `.app`-bundle check means a CLI tool essentially never shows as "installed" on macOS in the first place (CLI tools aren't `.app` bundles), so this path is rarely if ever reached there; not worth the extra complexity for a case that shouldn't come up.

Two more, for the in-app editor (see "In-app editor" below): `load_overrides(app: AppHandle) -> Result<Value, String>` and `save_overrides(app: AppHandle, overrides: Value) -> Result<(), String>`, reading/writing a small JSON file in `app.path().app_config_dir()` — created on first access via `fs::create_dir_all`. Both take the overrides object as opaque `serde_json::Value` rather than a typed struct since the frontend owns the shape (`{ [catalogId]: { hidden?, name?, category? } }`) and the backend only needs to persist it, not interpret it.

## Cross-platform support — Windows verified on hardware, macOS not

**Windows is verified by running the app** (v0.2.0): it starts, detects 68
installed programs with 65 real icons extracted from their `.exe`s, and
click-to-launch works. **macOS remains unverified** — there is no Mac to build
or run on, so its code has only ever been compiled in CI.

- **`tools/build_catalog.py` bin heuristics for dataset entries** (desktop-pkgs.json already carries `windows_winget`/`macos_brew` ids, which are package identifiers, not executable/app names): if `windows_winget` is present **and** the Linux bin looks like a plausible bare executable (`[A-Za-z0-9_]+`, no hyphens or version dots), guess the Windows bin is that name plus `.exe`. The name check matters: the Linux bin is frequently a *package* id (`dbeaver-ce`, `golang`, `intellij-idea-community-edition`), and emitting those as Windows bins produced entries that could never resolve — which is why most Windows tiles silently never appeared before v0.2.0. A missing guess is strictly better than a wrong one; the Windows system scan supplies exact paths for anything actually installed. If `macos_brew` is present, title-case the brew slug as a guess at the `.app` display name (`visual-studio-code` → `Visual Studio Code`; wrong for acronyms like `vlc` → `Vlc` instead of `VLC`). A small `BIN_OVERRIDES` dict hand-corrects the apps worth getting exactly right (currently Firefox, VS Code).
- **Windows system scan is the real source of truth.** `scan_system_apps_windows.py` reads the registry's Uninstall keys and extracts each app's own icon; `build_catalog.py` merges its results by matching the executable basename **or** the normalized display name (the latter is what actually works — see "Windows/macOS system scans" above), keeping the curated name/category and taking only the launch path and icon.
- **Start Menu fallback (Windows)**: when the exe can't be found on `$PATH`/`App Paths`, `windows_start_app(name)` looks the catalog display name up in `Get-StartApps` (run once, cached; classic shortcuts and UWP/Store packages alike) and `launch_app` starts it with `explorer shell:AppsFolder\<AppID>`. The match is exact on a normalized name (`norm_app_name`: drops `(...)`, arch/vendor filler and trailing versions) and is only tried for entries that have a `windows` slot in `bin`. A `windows` value of `start:<Start Menu name>` looks up that name instead of the catalog name (the catalog says "Affinity Studio", the Start Menu just "Affinity"; `Calculator` uses it too, so it gets the Store app's icon rather than the `calc.exe` stub's). An **empty** `windows` value means "exists on Windows, exe unknown" — `build_catalog.py` emits it for dataset entries that have a winget id but no guessable exe — so a Linux-only app that merely shares a name with a Windows one (KDE Dolphin vs the emulator; GNOME Files vs the Store app "Files") is never matched. A classic AppID (`{KnownFolderGUID}\rel\app.exe`) also yields the exe path, used for icon extraction. Remaining gaps: macOS resolution requires an exact, case-sensitive `<name>.app` in one of three fixed directories — no Spotlight/`mdfind` fuzzy matching.
- **Verification actually performed via CI** (see "CI: build and publish installers" below): `.github/workflows/release.yml` runs `cargo tauri build` on real `windows-latest` and `macos-latest` GitHub-hosted runners, both of which **compile and bundle successfully**. For macOS this is *build* verification only — nothing has clicked a tile and launched an app there. For Windows, runtime verification now supersedes it.

## In-app editor — hide / rename / recategorize

`catalog.json` ships inside the app's bundled resources (a system package's `/usr/share`, or embedded in an AppImage), which are **read-only once installed** — so an in-app editor can't write changes back into it. Instead, user edits live in a small per-user `overrides.json` in the OS-standard app config dir (`load_overrides`/`save_overrides` above), applied on top of `catalog.json` by the frontend at render time. `catalog.json` itself is never modified at runtime — the "single hand-edited file" design still holds for the *shipped* data, this just adds a second, user-writable layer on top of it.

- `main.js`: an `#edit-toggle` button in the header flips a module-level `editMode` flag and re-renders. In edit mode, each tile gets a hover-revealed toolbar (`.tile-toolbar`) with a hide button (✕, sets `overrides[id].hidden = true`) and an edit button (✎, swaps the tile for an inline form — name `<input>`, category `<select>`, save ✓ / cancel ✕ / reset ↺ buttons — in place, not a modal).
- A "Hidden apps" panel appears at the bottom of `#categories` only in edit mode, listing every hidden entry with an Unhide button — without this, hiding something would be a one-way trap.
- `effective(app)` merges `overrides[app.id]` onto the base catalog entry (`name`/`category`/`hidden` only — the override object can't inject arbitrary fields); every render recomputes this from the fixed `installedApps` list plus current `overrides`, so `is_installed` is only ever called once at startup, not on every edit.
- Escape cancels an open inline edit form; with no form open, Escape exits edit mode entirely (`editToggleEl.click()`).
- Reset (↺) deletes the entire override object for that id, restoring the catalog's original name/category/visibility in one action rather than needing per-field undo.

## Filter pills and CLI Tools

`cli: true` entries don't sit inside their assigned category (Development, Utilities, System, ...): `render()` splits them out (`cliApps` vs. `guiApps`) into one **CLI Tools card, shown first**, followed by the ten regular categories in their fixed order. They are a different kind of tile — clicking one opens a terminal instead of a normal window (see the Rust section) — and scattering them across categories they don't really belong to (is `tree` a System tool? a Utility?) only added confusion.

- **`All` / `GUI` / `CLI` pills** in the header (left of the search box, each with a count) choose what is shown: everything, only the categories, or only the CLI card. The choice is persisted in `localStorage` (`view`) rather than `overrides.json` — it is a display preference, like the search box's contents, not catalog data. Search and the pills combine: with `GUI` selected, searching for `git` finds nothing, because Git is a CLI tool.
- **Cards are dealt into columns by `layoutCards()`**, not CSS multi-column. Multi-column balances *height*, but tall cards can't split, so it filled 4 of 6 available columns and left the right third empty. Dealing each card into the currently shortest column uses the whole width, and on a 1920×1057 window the entire launcher fits on one screen. The column count is `floor((width + gap) / (270 + gap))`, recomputed on resize only when that number changes, and re-dealt after a search filters cards away so the columns stay even. Measured: 6 columns at 1900px, 4 at 1200, 2 at 800, 1 at 500.
- **CLI tiles show their own icon**, not just the generic glyph: a shipped `<id>.png` (`sync_icons.py` fetches these for CLI tools too — git, docker, python, ... — 27 of 50 at the moment), then the runtime fallback (`get_icon`, e.g. `hugo.exe`'s own icon), and only then the terminal glyph `category/cli-tool.png`. A non-CLI tile falls back to its category glyph instead (`fallbackIconPath` in `main.js`).

## Frontend — `src/index.html`, `main.js`, `style.css`

Plain HTML/CSS/JS, no framework, no build step. Flow:

1. `fetch('./data/catalog.json')`.
2. For each entry where `hidden` is not `true`, call `invoke('is_installed', { bin })` (parallelized with `Promise.all`).
3. Keep only entries that resolved `true`; group by `category` in the fixed 10-category order; skip categories with zero entries.
4. Render one `<section class="category">` per non-empty category (a bordered, rounded card — see layout below), each containing an inner CSS grid of tiles: a 34px icon (28px at ≤520px; CLI entries always get `assets/icons/category/cli-tool.png`, others try `icon`, `onerror` falls back to `assets/icons/category/<category>.png`) + name. The category heading itself is prefixed with a small emoji per category (`CATEGORY_ICONS` in `main.js`: 💻🎓🎨🌐🎮🎬📄🔬⚙️🧰) so a category reads at a glance even before the label text.
5. Click on a tile → `invoke('launch_app', { bin })`; on promise rejection, show a small inline error banner instead of failing silently.
6. A `#search` text input, centered in the header, filters tiles by name (substring, case-insensitive) live via `input` events; a category card hides itself when every tile inside it is filtered out; a "no apps match" message shows when the query matches nothing.
7. **Layout**: `header` is a 3-column grid (`1fr minmax(220px,420px) 1fr`) so `#search` sits truly centered regardless of the title's width, collapsing to a stacked single column below 520px. `#categories` uses **CSS multi-column** (`column-count`, not `display: grid`) with a column count that scales with window width — 1 by default, 2 at ≥700px, 3 at ≥1050px, 4 at ≥1350px, 5 at ≥1650px — and `section.category { break-inside: avoid }`. This is deliberate, not the obvious choice: a regular grid gives every card in a row the height of its tallest row-mate, so with 10 categories that vary a lot in size (some have 2 apps, some have 15+) a lot of the page height is empty padding next to short cards. Multi-column instead flows each card into whichever column is currently shortest, balancing total height across columns — this is what actually fixed the "grows too tall, needs a scrollbar" complaint, verified by screenshot (352 apps, zero scrolling at a normal window size). Each category card's own inner tile grid (`auto-fill, minmax(64px, 1fr)`, tuned small enough that even a narrow card fits at least 3–4 icons per row) is independent of the outer column count. A hover lift (`transform` + `box-shadow`) plus `cursor: pointer` gives tile affordance, `prefers-color-scheme` handles light/dark — no theme system beyond that for v1. *Superseded in part:* the column count is no longer set by breakpoints and the CLI section is now a side panel — see "CLI Tools panel" above and "Tile grid" below.

### Tile grid

Every tile is the same box everywhere, so icons and labels sit on a strict grid. `.grid` uses fixed-width tracks (`repeat(auto-fill, var(--tile-w))`, 80px) and fixed-height rows (`--tile-height`, 80px), with `justify-content: space-between` so spare width goes *between* columns and the first and last sit flush with the card's edges. Inside a tile the icon is a fixed 30px box at a fixed offset (`object-fit: contain`, so differently shaped artwork can't move it) and the label is clamped to two lines at 11px with an ellipsis (`-webkit-line-clamp`), the full name being in the tooltip; a long name can therefore no longer grow its row or push its neighbours around. Tiles were 96×98 with 40px icons before; the smaller size is what lets the whole launcher fit one screen. Measured on the running app: every visible tile 80×80. The inline editor is bigger than a tile, so it takes a 2×2 block of cells (`.tile-edit-form`). Below 520px the cell shrinks again (`--tile-w: 74px`, 28px icons).

### Theme adapter and icon backgrounds

The light/dark "theme adapter" the user asked about already existed by this point — it's just the `prefers-color-scheme` media query in `style.css` redefining the `--bg`/`--fg`/`--tile-bg`/etc. custom properties, no separate mechanism. Tile icons originally sat on a `background: var(--bg)` chip, which — since `--bg` already flips dark/light with the system theme — technically already satisfied "dark background behind icons in dark mode, light background in light mode." But the user's actual preference, once they thought about it, was simpler: no chip at all, just the bare icon. `.tile img`/`.tile-edit-form img`'s background changed to `transparent`. For icons that are a logo-on-transparent-canvas (most dashboard-icons/Iconify/system-theme icons), this removes the colored/white square that used to sit behind them, letting them blend into the category card. It has no visible effect on icons whose background is opaque and baked into the PNG itself (common for some app icons, e.g. a padlock inside a solid-colored rounded square) — that's part of the icon's own artwork, not something CSS can strip, and is expected/correct. The 10 category glyphs and the CLI-tool glyph are deliberately unaffected too: their colored background is intentionally part of the design (they read as a badge/placeholder, not a real app icon), not a chip layered on top by CSS.

## Desktop shortcut

A `.desktop` entry points `Exec` at the release binary directly (`src-tauri/target/release/app-launcher`, built via `cargo build --release` in `src-tauri/`) and `Icon` at `src-tauri/icons/icon.png`. The same file is placed both on `~/Desktop/` (double-clickable shortcut, matching the convention already used by other local projects: `Type=Application`, absolute `Exec` path, `Terminal=false`) and in `~/.local/share/applications/` (so it shows up in the KDE application launcher/search, not just the desktop icon). Re-run `cargo build --release` and the shortcut picks up the new binary automatically — no shortcut file changes needed after a rebuild, since the binary name itself doesn't change between builds.

This shortcut points at the raw dev/release binary, not an installed package — see "Installer packaging" below for the actual `.rpm`/AppImage artifacts. If the RPM is ever installed system-wide (`sudo rpm -i ...`), its own auto-generated `/usr/share/applications/app-launcher.desktop` would sit alongside this user-level one; XDG precedence means the user-level file in `~/.local/share/applications/` still wins for menu/search purposes, so no actual conflict, just two files with the same basename in different search paths.

## Installer packaging — `cargo tauri build`

`src-tauri/tauri.conf.json`'s `bundle.targets` is `["appimage", "rpm"]` (not `"all"`) — deliberately scoped to what's actually buildable on this Fedora machine without pulling in Debian's `dpkg-deb` tooling, which isn't native here. `bundle.category` is `"Utility"` (a freedesktop main category, same vocabulary discussed earlier) and `bundle.shortDescription` feeds the package/desktop-entry description.

- **Cargo package renamed** `app` → `app-launcher` (`src-tauri/Cargo.toml`) specifically because the default Tauri scaffold's binary name (taken from the package name) would otherwise ship as `/usr/bin/app` in the RPM — a generically-named binary that's a real collision risk in a system-wide install. No `[[bin]]` section needed; Cargo derives the binary name from `[package] name` automatically since there's a single `src/main.rs` target.
- **Real bug hit and fixed while packaging**: `cargo tauri build` failed outright on the AppImage target with `failed to run linuxdeploy`. The actual cause, only visible with `--verbose`: linuxdeploy bundles its own (older) `strip` binary, which can't parse the `.relr.dyn` section that this machine's very-new Fedora toolchain emits in shared libraries (a newer, more compact ELF relocation format) — every library it tried to strip failed, and linuxdeploy gave up. Fixed with the `NO_STRIP=1` environment variable (a linuxdeploy option that skips the strip step entirely) — `NO_STRIP=1 cargo tauri build`. If a future Rust/Tauri/linuxdeploy update changes this, the tell is the same: a wall of `ERROR: Strip call failed: ... unknown type ... section '.relr.dyn'` messages right before the generic bundling failure.
- **Verified**: both `app-launcher_0.1.0_amd64.AppImage` (~111MB, fully self-contained including webkit2gtk/gtk) and `app-launcher-0.1.0-1.x86_64.rpm` (~6.7MB, depends on system `libwebkit2gtk-4.1`/`libgtk-3`) build successfully; the AppImage was run directly and screenshotted showing the full working UI. The RPM's metadata (`rpm -qip`) and file list (`rpm -qlp`) were inspected but the package itself was **not** installed system-wide (would need `sudo`, not done this session) — install and first-run on a real system is still an open verification step.
- Output lives under `src-tauri/target/release/bundle/{appimage,rpm}/`, already excluded from git by the existing `src-tauri/.gitignore` (`/target/`).

## CI: build and publish installers — `.github/workflows/release.yml`

Triggers on a version tag (`v*`, a real release) or `workflow_dispatch` (manual run from the Actions tab, tagged `dev-<run-number>` and marked prerelease — how this was actually tested, without needing to cut a real release first). Creates/updates a **draft** GitHub Release and attaches every artifact below. `permissions: contents: write` at the workflow level so the default `GITHUB_TOKEN` can create releases with no extra secret needed.

Five jobs, all independent (no `needs:` between them — each one uploads its own assets to the same release tag via `softprops/action-gh-release`, which upserts rather than recreating):

- **`tauri-bundles`** (matrix: `ubuntu-latest`/`windows-latest`/`macos-latest`, via `tauri-apps/tauri-action@v0`): Linux gets `--bundles deb,rpm,appimage` (Ubuntu runners have `dpkg-deb` natively, unlike this Fedora dev machine, so `.deb` is only ever built in CI); Windows gets `--bundles nsis,msi`; macOS gets `--bundles dmg,app`. `NO_STRIP=1` carried over from the local packaging fix. `Swatinem/rust-cache@v2` caches the Cargo registry/target per workspace to keep repeat runs fast.
- **`arch-package`**: runs in an `archlinux:latest` container, builds `packaging/arch/PKGBUILD` via `makepkg` as a non-root user (makepkg refuses to run as root — the job creates a `builder` user, `chown`s the workspace, and marks it `git safe.directory` since checkout ran as root first), uploads the resulting `.pkg.tar.zst`.
- **`flatpak-bundle`**: runs in `bilelmoussaoui/flatpak-github-actions:gnome-47` (`--privileged`, needed for bubblewrap sandboxing), builds `packaging/flatpak/dev.d7.app-launcher.json` via `flatpak/flatpak-github-actions/flatpak-builder@v6`, uploads the resulting single-file `.flatpak` bundle.

**Real failures hit and fixed on the first two actual runs** (both triggered via `workflow_dispatch` and watched live via `gh run view`/`gh run view --log-failed`):
- Flatpak build failed with `error: failed to parse manifest ... feature 'edition2024' is required`. Root cause: the `gnome-46` container image's bundled Cargo (1.81.0) is too old to parse a transitive dependency's `Cargo.toml` requiring the edition-2024 feature. GNOME 46 is also flagged end-of-life by Flathub. Fixed by bumping both the container image tag and `runtime-version` in the manifest to `gnome-47` (confirmed available via the Docker Hub tags API before switching, rather than guessing a version and hoping the tag exists).
- After that fix, **all five jobs succeeded** on the very next run, including `windows-latest` and `macos-latest` actually compiling and bundling — see "Cross-platform support" above for what that does and doesn't prove.

**`packaging/arch/PKGBUILD`**: sources from the `master` branch via git (`source=("app-launcher::git+https://github.com/David7ce/app-launcher.git#branch=master")`, `sha256sums=('SKIP')` — the accepted pattern for a git-sourced PKGBUILD, not tied to a version tag) rather than a release tarball, so it always builds against current `master` with no PKGBUILD-version-vs-Cargo.toml-version to keep in sync. `pkgver()` derives a version string from `git rev-list --count`/`git rev-parse --short` per Arch packaging convention for git sources.

**`packaging/flatpak/dev.d7.app-launcher.json`**: base runtime `org.gnome.Platform`//47 (bundles WebKitGTK, unlike bare `org.freedesktop.Platform`) plus the `org.freedesktop.Sdk.Extension.rust-stable` SDK extension for the Rust toolchain. Builds with `--share=network` in `build-options.build-args` — this is **not** how a real Flathub submission would be built (Flathub requires fully offline, sandboxed builds via a `cargo-sources.json` dependency lockfile generated with `flatpak-cargo-generator.py`, so every crate is vendored ahead of time); allowing network access during the build is a deliberate shortcut for "produce a working `.flatpak` for direct distribution," not a step toward Flathub. Actually submitting to Flathub is out of scope unless asked — it's a separate review process on top of this.

## Explicitly out of scope (do not build without being asked)

- macOS **runtime testing or bug-fixing** — CI proves the code *compiles and bundles*, but nothing has clicked a tile and launched an app there; don't assume a macOS behavior report is accurate without checking on real hardware. (Windows is verified on real hardware.)
- `mdfind`/Spotlight scanning on macOS, and adding Start Menu entries that aren't in the curated dataset as new catalog entries on Windows — see `ROADMAP.md`.
- **Runtime** enumeration of installed software — the app itself still only ever does a targeted `is_installed` check against the fixed, pre-built catalog. `scan_system_apps.py` discovering apps is an offline maintenance step (like `build_catalog.py` or `sync_icons.py`), not something the running app does.
- Submitting the Flatpak to Flathub, or reworking its build to be Flathub-compliant (offline/sandboxed via `cargo-sources.json`) — the current manifest is for direct `.flatpak` distribution only.
- Installing/testing the `.rpm`, `.deb`, or Arch package on a real system — CI proves they *build*; nothing has installed one and launched the app from a real package manager yet.
- Keyboard shortcuts (beyond native text-input behavior in the search box), tray icon, autostart.
- Any runtime network access (icon fetching, update checks, telemetry) — `scan_system_apps.py` itself makes none either (everything it reads is local).
